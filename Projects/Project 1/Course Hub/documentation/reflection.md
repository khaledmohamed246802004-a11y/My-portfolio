# Project Reflection (300–400 words)

Building the Accessible Course Mini-Site helped me understand that semantic HTML is not simply a way to organise code; it gives the content meaning that browsers and assistive technologies can recognise. I used landmarks such as `header`, `nav`, `main`, `aside`, and `footer` to identify the main areas of each page. Headings provide an outline that makes the content easier to scan. On the schedule page, table captions and header cells explain the purpose and relationships of the timetable data. In the registration form, labels, `fieldset`, and `legend` make controls and related choices understandable. If these elements were replaced with generic `div` elements, the visual layout might look similar, but users of assistive technology would lose much of this built-in structure and developers would need to recreate it with extra ARIA and careful coding.

Testing was important because a page that looks correct is not automatically accessible. The four HTML pages were reported to pass the Nu HTML Checker with no errors or warnings. The 21 registration-form test cases were reported as passing in both Chrome and Safari. Keyboard checks, including Tab, Shift+Tab, visible focus, and the skip link, also passed across the four pages. VoiceOver content navigation was confirmed on all four pages in Safari; heading navigation was tested successfully, and the VoiceOver Rotor was opened. The form's GET submission was also tested: after submitting fictional test data, the browser displayed the submitted `name=value` query string in the address bar.

One concrete issue appeared during the contrast review. The original accent colour `#0f766e` against the soft background `#dce9e7` measured 4.39:1, which is below the 4.5:1 WCAG AA requirement for normal text. I changed the shared accent to `#0f6b63`; the new combination measured 5.10:1. This showed why contrast needs to be measured rather than judged only by appearance.

I deliberately did not collect information such as a home address, phone number, date of birth, identification number, or payment details because these details are unnecessary for a sample course-session registration. Collecting less personal data reduces privacy risks. If I continued improving the site, I would capture clearer evidence screenshots for each validation and accessibility check and review additional form-control and focus-state contrast combinations. Overall, the project showed me how semantic structure, native HTML validation, keyboard support, and careful data minimisation work together to create a more accessible experience.
